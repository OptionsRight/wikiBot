# wikiBot 开发交接

更新日期：2026-09-27\
规范性设计：[完整设计 v0.4](domain-knowledge-bot-design-v0.4.md)\
状态：已有单机实现、真实模型/Wiki首跑和历史企微合成数据联调；并行补齐中，尚无上线验收结论。现行规则以 ADR-0004、spec.md 与各任务证据为准。

## 1. 开发范围

沿用自研方案、公司模型和用户现有 llm-wiki skills 维护的唯一知识源。首个广告领域覆盖新渠道接入、腾讯广告新增代理商、腾讯 RTA 新增策略。2026-09-26 用户确认日常更新通过技能完成；发布助手对接实际 Markdown 知识目录与技能维护入口，不以早期研究的桌面应用为必需依赖。

必须覆盖不同人群的表达风格、普通成员/知识管理员两种权限、反馈、独立问题登记和管理员从 bot 发起的知识维护。bot 承接维护发起与状态查询，网页承接最终差异复核和发布。当前模型传输为固定版本 pi-ai，由 ModelGateway 隔离，多跳工具循环为后续预留。

本轮新增的 v0.4 是当前完整设计。历史文件保留作依据；审查中的 F1–F5 已补充设计契约，仍待实现和验证。

2026-09-26 两轮设计访谈 Q1–Q7 已确认并写入 v0.4，本轮审查树已收口，详见[访谈记录](../../reviews/wikiBot-v0.4-grill-2026-09-26/REVIEW.md)。实际流程支持范围、Schema、兼容性、容量及公司运维参数仍须按阶段 0 和实施验收完成，不能将设计确认作为实现通过证明。

## 3. 实施顺序

### 阶段 0：兼容性与核心契约

预计 4–6 个工程人日，已包含在总预算中。完成：

1. 公司模型真实调用、取消、完整结构块与代表性长流程延迟测量。
2. 企微用户映射、稳定入站消息 ID、累计流式、回执丢失及重连实验。
3. 从实际 llm-wiki skills 维护的目录导出，验证改名、引用、技能受控更正、重新摄入及再次导出的真实往返；source-docs 原始存档仍只读，更正材料按实际技能协议独立保存。
4. 评审流程节点完整性、发布 epoch/领域锁、接收事务、worker fencing 和未知交付语义。
5. 记录依赖版本、成功/失败样例、限制、测试档位和调整后的估算。

退出条件：三条外部链路有可复查结果，关键失败路径有明确处理；尚不满足条件的能力不能作为已验证前提进入承诺排期。

### 阶段 1：知识基线与一个流程贯通

先挑选一个经负责人确认的真实流程。实现快照→复核→构建/评测→激活→问答→引用→反馈→修订写回→再次复核发布。

知识包为 pages + 金样例 cases + config。检索页面加单次模型调用，协议及引用校验后交付；金样例对照预期判定，运行完成不代表质量通过。人工基线包含知识不足、冲突、澄清、多轮历史有效性和禁止结论。

### 阶段 2：角色、风格与双渠道

完成普通成员/管理员授权、业务/技术视角、解释深度、本人偏好、会话隔离、网页与企微单聊。三个首批流程在各自批准支持范围内均具备完整必要步骤。

验证直接 API、模型工具、旧按钮及异步任务的授权；风格变化不能扩大权限或删去必需节点。

### 阶段 3：反馈和知识维护完整链路

完成答案反馈、无答案也可登记的问题、本人/管理员工单页面、补材料、处理/确认/重开、管理员主动知识修订，以及写回、复核、发布、撤回、回滚和通知状态。

工单、修订、发布与交付独立保存，模型故障不妨碍基本登记。发布成功不能自动等同于用户问题解决。

### 阶段 4：完整范围验证

完成群聊受众、完整附件/来源/改名场景、故障恢复、声明负载下的联合 SLO、恢复演练及第二个非广告领域的配置接入。

若采用单领域受控试点分期，应明确群聊、第二领域等尚未验收范围；权限、完整性、并发和基本恢复须在试点前完成。

## 4. 必须保持的实现约束

- 角色、偏好、回答模板分别存储，服务端授权覆盖每个对象和异步执行。
- 请求先固定不可变 ReleaseDescriptor，再读取模型、模板、检索和协议配置。
- 激活、撤回、回滚共用领域锁和单调 publish_epoch；撤回后的空指针可以发布新修复版本。
- Inbox、Answer/业务对象、Job、审计及必要 outbox 使用明确事务边界。
- worker 持久化写入和投递入队由租约与 fencing_token 约束，旧执行者不得覆盖状态。
- 完整块先持久化再外发；投递失败/未知与业务结果分离。
- 企微每个 bot 只有一个连接拥有者，累计流内容按序发送，按实际 UTF-8 字节和回执判断交付。
- 实际外发、网页重放和历史读取都检查当前授权与撤回状态。
- 来源修订保留基线哈希和专家更正，最终审批绑定实际快照；助手不能直接激活线上版本。
- 生成成功、清单完整、交付完成、用户确认解决分别记录。
- 不恢复 ProcedureSpec 或互斥路径引擎；无命中返回缺口，有命中但不足时澄清/说明不足，业务不适用必须有依据。
- 当前可用历史仅帮助理解自由文本追问；换对象/纠正以本轮为准，历史不升级为知识依据。
- 恢复旧备份后先确认当前撤回与授权状态；旧 pending 不证明未执行，可信执行证据不足时不能自动重放写操作。
- 已知模型变化时暂停受影响的新生成、候选激活及不合格回滚；重新验证并发布配置后恢复，不悄然切换模型。
- 支持范围在测试前冻结；范围内失败不能改记范围外以移出普通问答 SLO 分母。
- 历史选取及调用模型前均重验授权、撤回、模型复核和交付范围；未交付/unknown 正文不得用于新生成。
- 模型待复核历史答案只向原获准受众展示已交付内容并加标记，暂停未交付正文、停止无法确认模型资格的在途生成；新模型回归不自动批准旧答案。

## 5. 交付物与验证证据

| 交付物 | 最低要求 |
|---|---|
| 应用与数据库迁移 | 按设计模块划分；部署后可重复初始化/升级；事务与唯一约束覆盖关键对象 |
| 业务契约与 JSON Schema | 页面/金样例/配置、回答协议、API、错误码、版本条件和工具范围 |
| 公司模型/企微适配 | 固定版本、脱敏实测记录、取消/重试/未知结果说明 |
| 发布助手 | 工作区配对、快照、稳定 ID、来源修订、冲突和部分写入恢复说明 |
| 人工评测基线 | 三个流程、30–50 条真实问题及独立故障/权限案例；正确依据由负责人核对 |
| 验收记录 | v0.4 第 10.3 节矩阵；质量与声明负载的测量结果 |
| 运维说明 | 配置、密钥注入、监控、任务恢复、撤回/回滚、备份与恢复演练 |
| 容量报告 | 模型/配置版本、配额、并发、内容长度、P50/P95/P99、联合达标率与失败分布 |

普通请求的正式目标为至少 95% 同时满足首段有用内容 ≤3 秒、完整回答 ≤10 秒和成功。计入排队、超时、故障；不能靠快拒答、空提示或企微只发链接达标。知识与质量正确性优先通过真实试题验证，不能用同题重复压测替代。
