# wikiBot v0.3 落地成本估算

日期：2026-09-25\
依据：当前本地 v0.3 设计与实施前审查。\
性质：工程量级估算，尚未通过真实接口实验校准；不构成已完成开发、通过验收或供应商报价。

## 1. 结论

维持现有自研方案，完整 v0.3 建议预留 **85–125 个工程人日**；两名有相关经验的全职工程师，预计 **11–16 个工作周**。另需业务知识负责人投入与公司接口、部署协同。

如果分期交付，先完成单领域受控试点，预计 **50–75 个工程人日、两人 7–10 个工作周**。试点包含不同人群的回答风格、普通成员/管理员权限、反馈、独立问题登记，以及管理员通过 bot 发起知识更新的完整路径。

上述工程人日已包含联调、验收工作及约 20% 风险储备，并向上取整。完整版本数字是从现在起的累计投入，不能再与试点投入相加。

当前工作区主要是设计与审查文档，未发现应用代码、数据库迁移或可复用的已验证实现，因此按从设计进入开发估算。若另有可复用的代码或公司基础服务，需要核对后扣减对应工作量。

## 2. 估算前提与范围

- 一个工程人日按约 8 小时计，涵盖开发及本项目必要的技术验证。工作周为 5 个工作日。
- 采用现有 TypeScript 模块化服务方案，使用公司模型；Pi 保留为可替换的模型调用适配候选。
- 首批知识为一个广告领域的三个流程，有能够确认流程、分支及纠错依据的业务负责人。
- 公司能够提供实际模型接口、企业微信机器人、身份映射或 SSO，以及正常的部署、数据库和存储条件。
- 网页使用标准管理界面，首版追求可用与清晰；估算未包含定制视觉设计或复杂移动端。
- 两名工程师应覆盖后端、网页和集成能力；测算按每周合计约 8 个有效工程人日，给评审、沟通与依赖等待留出空间。
- 接口开通、采购、公司审核与专家长期缺席造成的日历等待另计。
- 用户规模、模型配额和实际并发尚未确认，以下数字不能同时被解读为容量承诺。

| 内容 | 单领域受控试点估算 | 完整 v0.3 估算 |
|---|---|---|
| 领域与渠道 | 一个广告领域、三个流程，企微单聊与网页 | 再用第二个非广告领域验证配置接入；完成设计中的群聊场景 |
| 人群与权限 | 业务/技术视角、解释深度、两种角色、个人偏好和基本会话 | 完善各入口、领域、历史访问与权限变更的组合验证 |
| 反馈与问题登记 | 两种登记入口、本人/管理员页面、处理/解决/重开及状态查询 | 完善等待补充、合并、内部备注、附件和通知异常等全部交互 |
| 管理员知识更新 | bot 草稿→来源写回→快照→网页复核→发布；助手手动运行，冲突人工处理 | 完成设计列出的改名、链接、来源摘录、静态附件及多候选并发场景 |
| 发布与可靠性 | 版本固定、复核绑定内容、撤回/回滚、基本幂等与恢复必须有效 | 扩展故障覆盖、运维恢复、历史失效通知与组合回归 |
| 质量与性能 | 30–50 条人工基线，加权限/故障用例；在声明的试点负载下测量 | 完成设计要求的负载档位、长流程、群聊、发布并发及跨领域验证 |

试点列是分期建议，并非把当前设计悄然改成更小的验收范围。若群聊、完整附件处理及第二领域必须在首日交付，应采用完整版本的预算。

完整性、授权和知识发布的一致性不能通过缩小界面或减少用户数而免除。试点涉及的 F1–F5 契约须落实，不能把未解决的设计问题直接推入使用环境。

## 3. 工程工作量拆分

各行按主要责任归类：身份行负责授权规则，渠道行包含网页界面；工单行负责业务状态和接口；知识行负责来源/版本/发布逻辑。末两类负责跨模块验证与基础可靠性，避免把同一页面或测试重复计算。

| 模块 | 试点人日 | 完整版本人日 | 主要成本来源 |
|---|---:|---:|---|
| 设计收口与真实接口验证 | 4–6 | 4–6 | 关闭关键契约缺口，验证模型、企微和 llm_wiki 往返 |
| 问答、检索、流程完整性、引用与风格 | 6–9 | 10–15 | 完整流程检索、结构化分段校验、引用及不同表达模板 |
| 身份、角色、会话与偏好 | 4–6 | 6–9 | 跨端身份、领域权限、历史访问范围与当前授权复核 |
| 企业微信适配与网页界面 | 5–7 | 8–12 | 消息连接、流式回执、问答与工单/复核管理页面 |
| llm_wiki 发布助手、管理员修订与知识发布 | 8–12 | 14–20 | 快照、基线冲突、来源纠错、评估、激活、撤回和回滚 |
| 反馈、独立问题登记与工单处理 | 4–6 | 7–10 | 可访问答案关联、无答案登记、处理状态及角色动作 |
| 幂等、任务恢复、通知与审计 | 4–6 | 8–12 | 持久化任务、重试、结果未知、角色变更及失败告警 |
| 质量验证、联调、压测与部署 | 6–8 | 8–12 | 人工基线接入、端到端回归、故障验证、负载测量和恢复演练 |
| 第二领域接入与配置化验证 | 0 | 3–5 | 用真实第二领域验证配置能力，修正广告特定假设 |
| **基础合计** | **41–60** | **68–101** | 已计必要测试与部署 |
| **含约 20% 储备并向上取整** | **50–75** | **85–125** | 用于预算与初始排期 |

知识专家整理事实、核对业务流程及人工确认答案的工作不计入工程人日。工程师接入评测样本与运行测试计入表内。

## 4. 排期与人力预算

| 配置 | 单领域受控试点 | 完整 v0.3 |
|---|---:|---:|
| 一名工程师，按每周约 4 个有效人日 | 13–19 周 | 22–32 周 |
| 两名互补工程师，按每周合计约 8 个有效人日 | 7–10 周 | 11–16 周 |

增加人数无法线性压缩模型验证、知识确认、来源写回和发布验收等依赖链。首轮建议两名工程师协作，并指定一名有决策权的知识负责人。

计算公式：工程成本 = 工程人日 × 公司实际综合人日成本。

以下只用 **1,500 元/人日** 演示换算，数值不是市场工资或外包报价：

- 试点：50–75 × 1,500 = **75,000–112,500 元**。
- 完整版本：85–125 × 1,500 = **127,500–187,500 元**。
- 两个数字均已含表内储备，不能再加一次相同的 20%。
- 内部团队的工资分摊与机会成本，不等同于项目当期新增现金支出。

首批三个流程另预留知识专家 **5–10 人日**：包括确认前置条件与分支、整理更正依据、审核 30–50 条问答和参加业务验收。这个区间假设原始资料可用；如果流程本身尚未统一，须单独估计梳理工作。第二领域的专家投入按其实际知识规模另计。

公司 IT/运维接口协调可先预留 **2–4 人日**，作为工程团队之外的协同投入；实际部署和恢复实现已在工程表内，不重复收费。

## 5. 持续运行成本

### 5.1 模型用量

模型账单取决于公司选定模型和内部结算方式，目前缺少实际单价。用量公式为：

每月模型费 = 月请求数 ×（平均输入 tokens × 输入单价 + 平均输出 tokens × 输出单价）÷ 1,000,000。

单价均按“元/百万 tokens”。例如按每天 1,000 次、每月 30 天、每次平均 6,000 输入和 1,000 输出 tokens：

- 基础输入量：180,000,000 tokens。
- 基础输出量：30,000,000 tokens。
- 基础月费：180 × 输入单价 + 30 × 输出单价。
- 若为重试、补充调用及评测暂留 20% 用量，则规划月费为 216 × 输入单价 + 36 × 输出单价。

上述调用量、上下文长度与 20% 余量是预算情景，不是实测值。发布评测、知识整理、embedding（若启用）和 llm_wiki 的模型消耗须汇总核算，更新密集时不能假定 20% 一定够用。业务量若是每天 100 次，该问答用量情景可除以 10。并发能力需另行测量。

### 5.2 基础设施

首轮部署所需的逻辑资源为入口/API、异步 worker、关系数据库、不可变内容及附件存储、日志监控和备份；各进程如何共用主机由试验结果决定。

可复用公司已有资源时，按实际配额与内部成本分摊。需要单独购买云资源时，先根据阶段 0 的部署和负载结果选择规格，再查对应供应商报价。当前没有云厂商、区域、可用性要求和保存容量，不能给出有依据的固定月租。上述人力金额不包含这些资源费用。

### 5.3 人工维护

单领域初期可作为排班假设预留：

- 工程维护：每月 **2–4 人日**，处理告警、依赖变更、失败任务、备份恢复与质量回归。
- 知识负责人：每周 **0.5–1 人日**，处理反馈、补全知识、复核和发布。
- 新增领域、较多问题积压或频繁业务变更按实际增加。

维护工时还没有运行数据支撑，应在试点后按真实工单量和知识变化频率调整。产品新功能开发不计入日常维护配额。

## 6. 哪些因素会改变估算

| 因素 | 对成本的影响 | 收口方式 |
|---|---|---|
| 公司模型无法实现当前分段协议或达到时延目标 | 可能要求调整模型、调用方式或产品目标，不能承诺加几个开发日就达标 | 用代表性的真实问题先测首段、整答与排队时间 |
| llm_wiki 纠错再次导入不能保留专家修改 | 影响唯一维护源与发布闭环，是关键路径 | 实测来源更正、重新导入、改名和引用 |
| 企微身份映射、群受众或通知能力不符合预期 | 影响渠道与权限设计，外部开通等待还会延长日历时间 | 使用实际租户验证；确认首期单聊/群聊范围 |
| F1–F3 的流程完整性、发布并发、崩溃恢复未落实 | 后期补救可能返工核心数据模型及接口 | 在稳定核心接口前落实契约和反例 |
| 原始知识存在矛盾或没有明确负责人 | 主要增加专家工时与等待，技术实现无法自行确定正确业务规则 | 指定负责人，对三个流程逐一确认 |
| 高可用、多地域、细到页面的复杂权限或连接更多业务系统 | 超出本次 v0.3 估算前提 | 另列增量范围和预算 |

Pi 的接入位于设计验证和模型调用模块中。当前多数工程成本来自业务状态、权限、知识维护和真实渠道验证，单独替换或移除 Pi 不足以显著缩短整个项目。

## 7. 建议的预算收口方式

先执行表内已计入的 **4–6 个工程人日** 验证：

1. 使用公司真实模型跑长流程、两类风格和完整结构化输出，记录端到端耗时。
2. 打通企微身份映射、流式交付、重连和回执。
3. 对一个真实流程贯通 llm_wiki 导出、专家纠错写回、重新导入与再次发布。
4. 确定流程完整性、版本并发和任务恢复的最小可执行契约。

验证后更新人员、工期和运行配额。若关键能力不满足，先明确设计调整，再给固定排期。前面讨论的“现成平台 1–2 周试点”不能用于当前从零自研方案。
