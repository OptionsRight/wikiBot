# 13：成员登记独立问题并跟踪处理

**What to build:** 成员无需既有答案即可在网页主动登记问题，处理人分诊并给结果，由报告人确认关闭、撤回或重开。

**Blocked by:** 04：成员登录并进入有资格访问的领域。

**Status:** in-progress

**交付阶段：** 试点。依据为 2026-09-26 两轮访谈修订后的 wikiBot v0.4，设计约束及任务拆分已由用户的 implement 指令确认。

**用户故事：** US-28、US-30、US-31、US-32（实施规格编号）。

**外部前提：** 试点工单处理人、分类与处理范围；持久化和身份环境沿用已建服务。

## Acceptance criteria

- [ ] 只有用户明示动作才创建工单；无 answer_id 或模型不可用仍可登记，问题内容和类型可校验。
- [ ] 创建使用按主体/领域/操作限定的幂等键与请求摘要，工单、初始事件、通知 outbox 同事务；重复通知不重复工单。
- [ ] 成员仅看本人工单和允许的材料；领域处理人按当前能力处理，跨域管理员与猜测 ID 不能越权。
- [ ] 网页贯通 submitted、triaged、in_progress、waiting_reporter、resolved、closed；管理员 resolved 需可核验结果，报告人确认关闭或重开，撤回不记为已解决。
- [ ] 支持成员补充文字、处理人分派/请求材料和查询进度；普通问题不会被模型自动登记，也不自动生成知识修订。
- [ ] 状态变更与审计原子提交，通知失败只重试通知；用户能够查询真实结果，不因通知丢失重新执行业务。
- [ ] 统计明确区分解决确认、撤回、重开与未解决积压，不把工单关闭解释为广告业务操作完成。

## 验证方式

从成员与管理员公开入口完成登记→处理→补充→解决→关闭/重开，包含模型离线、重复提交与权限反例。

验收结果须记录实际配置/版本、执行环境、预期与实得、证据及剩余阻断；未实现、未运行或外部前提缺失不能标为通过。用例集中于公开业务行为和真实适配契约，避免为内部实现细节建立镜像测试。
