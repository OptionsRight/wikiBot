# 25：通过配置接入第二个非广告领域

**What to build:** 第二领域负责人通过现有配置、发布入口、角色及 bot 绑定接入同一框架，成员取得本领域知识并与广告领域隔离。

**Blocked by:** 08：知识不足、来源冲突与必要澄清；16：更正写回来源并经复核发布生效。

**Status:** blocked

**交付阶段：** 完整范围。依据为 2026-09-26 两轮访谈修订后的 wikiBot v0.4，设计约束及任务拆分已由用户的 implement 指令确认。

**用户故事：** US-01、US-02、US-03、US-06、US-08、US-21、US-22、US-48（实施规格编号）。

**外部前提：** 第二个非广告领域、真实知识与负责人、代表性问题、独立 bot 及领域授权配置。

## Acceptance criteria

- [ ] 按既有平台权限创建领域、配对工作区、提交复核、评估发布，再由稳定入口绑定 bot，不修改核心框架代码或写领域专用分支。
- [ ] 配置本领域称谓、两种视角/深度模板、角色与访问范围；模板和知识纳入本领域发布描述与评估。
- [ ] 真实问题覆盖本领域问答、引用、缺知识、明示登记和管理员修订写回发布；不复用广告结论冒充领域验证。
- [ ] 跨域成员、A 域管理员、助手凭据、工具读取、偏好与私人上下文均按各自范围限制，不能由绑定地址扩大权限。
- [ ] 部署与性能报告记录本次新增领域的实际量级；若必须改核心代码则记录通用性缺陷并修复后重验，不能称配置化通过。
- [ ] 交付负责人核对的第二领域证据，与广告领域并行请求验证知识、会话、工单与发布隔离。

## 验证方式

真实第二领域从零配置到成员问答和一次来源修订闭环；包含 A-02 的跨域场景。

验收结果须记录实际配置/版本、执行环境、预期与实得、证据及剩余阻断；未实现、未运行或外部前提缺失不能标为通过。用例集中于公开业务行为和真实适配契约，避免为内部实现细节建立镜像测试。

## 范围边界

不做跨领域联合回答；不存在第二领域资料时不使用虚构领域宣称通过。
