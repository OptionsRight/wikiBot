2. [高级模型聚焦复查](./domain-knowledge-bot-review-v0.2.md)：R1–R6 的关闭理由、最后两处一致性修正及仍待实测事项。
3. [HTML 设计展示](./domain-knowledge-bot-design.html)：与设计基线对应的可视化阅读版本，包含架构图和两轮评审原文。实施以 Markdown 契约为准。

如果文件缺失，先按上述文件名查找或请用户提供，不根据本交接摘要重建规格，也不要把预览服务地址当作产品接口。

- 首轮评审提出 2 项 P1、4 项 P2；修订后六项均在设计层面关闭。复查补充的两处文字契约一致性问题也已修改并再次核对。细节直接见评审记录，不在本文重复。
- 当前结论是可以进入阶段 0 兼容性验证及首版实施；不是生产上线批准，也不是性能达标证明。
- 已交付的 HTML 是设计文档展示，不是 Bot 产品原型或应用前端。其导航与评审展开已在浏览器检查。
- 产品仓库已确定为 `OptionsRight/wikiBot`，本次初始提交仅包含交接材料。尚未开发 Bot 产品代码，未固定实际依赖版本；没有数据库迁移、公司接口联调或模型压测结果。文档生成脚本不属于待接手的产品实现。

## 3. 不要把早期讨论当成最终决定

完整最终决策已集中在设计稿 §1，接手时尤其注意这些对话修正：

- 早期推荐过 Dify，用户明确否定；后续已转为 Pi SDK 的代码实现路线。
- 用户曾选过“偏好 + 任务进度”记忆，之后明确取消任务进度。以最终设计的个人偏好和当前会话边界为准。
- 最初讨论单一广告 Bot，后续扩展为复用 llm_wiki 的通用框架；每领域独立企微 Bot，共用后端。广告是第一个验收领域。
- “只提供 Wiki 地址”已经细化成发布入口契约；不要接回工作人员桌面的 localhost API，也不要假定公司凭据、负责人和授权可以从 URL 自动生成。

这些是防止恢复已放弃方案的上下文，不需要重新对用户进行一轮完整需求访谈。

## 4. 接手后的第一轮工作

1. **在本仓库开展实施。** 目标是 `OptionsRight/wikiBot`，本次交接时仓库尚无产品实现。先检查接手时是否已有 AGENTS.md、技术栈和测试约定，再在仓库内建立产品结构；`docs/handoff/` 仅用于交接材料，不作为产品源码目录。
2. **按照设计稿 §9 阶段 0 做验证。** 将 Pi/公司模型、企微、llm_wiki 工作区往返三个验证拆成可独立复现的小实验，固定实际使用的包版本和样本。验收输出必须包含真实记录、失败路径和能力缺口，而不是只有“调用成功”。
3. **先形成一条可验证的纵向链路。** 沿设计规定的 pending 领域、受控快照、复核发布、领域问答和引用展示逐步实现；之后再补完整角色偏好、反馈回写及第二领域接入。不要另起一套需求或审批平台。
4. **用评审报告驱动关键测试。** 将各项“留到验证阶段的事项”以及设计 §9 的上线检查转换为有结果的测试/联调记录。普通文案改动不必建立镜像测试。
5. **记录可运行交付。** 给出启动方式、配置样例、迁移和种子数据、测试命令，以及已通过/未验证清单；不得提交真实凭据。

如果公司接口或工作区尚不可用，可以继续做接口适配层、脱敏样本和本地自动化测试，但必须明确标记 mock。模拟成功不能关闭真实兼容性或性能验收项。

## 5. 实施前仍缺的输入

完整清单见设计稿 §10。接手时优先收集能够解锁阶段 0 的材料：

- 公司批准的模型服务文档/测试连接方式及配额；密钥通过公司规定的安全方式配置，不写入交接文件。
- 实际使用的 llm_wiki 版本及一个可用于验证的脱敏工作区。
- 企业微信 Bot 类型、测试入口及身份/群范围映射办法。

知识规模、峰值并发、embedding 可用性和保留制度影响后续配置及容量承诺，未获确认前沿用设计中明确标注的“假设/建议值”，不得把它们升级为用户承诺。可以把缺失输入合并询问，并继续不依赖它们的本地工作。

## 6. 验证和决策纪律

- 设计评审通过与代码/接口/性能验收分开记录。
- 对公司模型实测后才能承诺延迟和并发，使用设计 §7 的联合达标口径；不要用状态提示、过快拒答、剔除失败请求或截断步骤美化结果。
- 若上游实际能力与设计不符，记录具体证据、影响和最小调整。只有影响已确认产品边界时再请用户作决定。
- 保留“知识维护源 → 经复核发布版本”的单向在线读取边界；反馈回写不是让在线问答实例获得发布权限。详细机制见设计和评审，不另行发明替代流程。
- 用户偏好直接推进具体工作，避免反复请求已获授权的动作；遇到确实缺失的业务决定时，说明缺什么及影响。

## 7. Suggested skills / 建议调用的技能

以下为按阶段建议，不要求全部调用。新环境先检查技能是否可用并阅读相应 SKILL.md；同名技能可能路径不同。

| 技能 | 建议使用时机 |
|---|---|
| `codebase-design` | 首次落入代码库时，确定模型适配、知识发布、会话与反馈模块的接口边界。 |
| `tdd` | 实现发布基线检查、幂等、会话隔离、偏好范围和统计口径等关键行为时，先建立能验证约束的测试。 |
| `diagnosing-bugs` | Pi/公司模型、企微或 llm_wiki 联调失败，以及首段/整答延迟不达标时，用证据定位瓶颈。 |
| `code-review` | 有真实代码变更和固定比较基线后，按设计规格及仓库规范做交付前审查；设计评审不能替代代码审查。 |
| `handoff` | 跨会话继续开发或转交其他 agent 时，更新进展、验证结果和剩余问题，引用现有规格而非复制正文。 |
