**F1 · [P1] 流程完整性和无引用澄清的判定尚不能执行**

依据：[流程页面要求 L105–109](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L105)、[答案及分段校验 L169–175](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L169)、[上线条件 L301–303](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L301)。

文档要求关键前置条件与步骤不得遗漏，并要求必要步骤无法完整输出时将答案判为失败。实际规定的在线检查只有块类型、引用是否属于已取回证据、版本有效性。它们无法判断一份正常结束的回答是否漏了步骤；页面模板也没有定义可用于比较的步骤标识和分支要求。

反例：已发布流程包含 A 前置授权、B 配置、C 校验。模型只输出 B、C，引用均为合法页面且正常结束。现有检查会全部通过，却没有规则能把它判成“不完整”。另一个边界是模型把操作建议标为 `clarification` 并使用空引用；单纯校验枚举值不能证明这段文字确实只有澄清问题。

最小修正：先给三个试点流程维护经过人工确认的结构化清单，至少表达适用条件、缺失输入、必要前置条件、分支、步骤 ID 和完成标准。完整清单可以由程序按已确认分支展示，模型负责解释。若采用生成式清单，必须定义必需项的覆盖判断和终态；不能仅凭模型发出结束标记判为完整。无依据澄清宜由程序根据缺失字段生成，或限制为可验证的澄清结构，不能只相信模型给出的类型。

这不等于结构校验可以证明答案语义正确。步骤内容、分支选择与证据支持程度仍需要人工核对的质量评估。建议分别记录“协议有效”“清单完整”“发送完成”，避免一个 success 字段承载三种含义。

关闭证据：构造“遗漏前置条件但引用合法”“澄清块夹带操作指令”“正常结束但缺少最后一步”“无效分支”“长度预算耗尽”等样例，均不得判作完整流程答案；三个真实流程的必要内容可以完整交付。

**F2 · [P1] 激活、撤回和回滚缺少共同的并发契约**

依据：[版本状态与激活 L128–136](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L128)。

父版本 CAS 和领域串行激活已经解决了两个发布者覆盖的问题。但文档没有明确撤回、激活、回滚是否共享同一个领域锁或版本计数，也没有定义“依赖相同失效依据”的可计算标识。整版本撤回后 active 指针如何处理、修复候选如何通过父版本比较，也需要统一。

一种被当前文字允许的实现时序如下。它不是已执行的代码测试：

| 顺序 | 激活事务 A | 撤回事务 B |
|---|---|---|
| 1 | 读取候选 ready，读取父版本和依赖有效 | |
| 2 | | 撤回父版本，标记相关候选不可用并提交 |
| 3 | 只按旧 active 指针执行 CAS，随后写候选 active | |
| 4 | 旧依赖内容可能被重新激活 | |

如果所有操作已在同一领域锁内完成，或在同一个代际计数上做条件更新，上述时序就会被挡住。但“在同一事务内检查”本身没有规定这种隔离；普通读取和后续写入之间仍可出现并发变化。

最小修正：给领域发布状态一个单调递增的 `publish_epoch` 或等价版本字段，激活、撤回、回滚使用共同的领域级互斥与条件更新；候选、审批、评估绑定该基线。首版可以保守规定：紧急撤回提升代际并使该领域未激活候选全部过期，新候选基于修正后的内容重新复核。这样无需新增复杂的语义依赖失效系统。明确撤回后的服务指针状态以及修复版本的基线规则。

关闭证据：覆盖“两个候选交错激活”“激活检查后撤回先提交”“撤回后尝试旧回滚”“没有可用版本后发布修复版本”，验证不会重新服务失效内容，修复也不会被父版本比较永久卡住。

**F3 · [P1] 幂等与崩溃恢复只有目标，缺少持久化状态和失败语义**

依据：[任务表/outbox L56](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L56)、[消息去重 L187](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L187)、[断流处理 L251](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L251)、[接口 L279–282](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L279)。

文档要求回调重试不重复生成答案，也要求断流后可以查询最终状态。但没有 Answer/Attempt 的状态迁移、工作者失联接管、网页请求幂等和发送结果不确定时的处理。写了 outbox 还不能直接保证外部消息只投递一次。

三个必须回答的故障窗口：

- 消息 ID 已记为处理过，生成任务还没持久化，进程崩溃：重放回调是被永久忽略，还是能够恢复？
- 模型已生成或部分答案已外发，结果尚未保存，进程崩溃：何时结束旧尝试，是否允许重新生成，用户最终看到哪个答案？
- 企微已经收下通知，但回执丢失：重试是否再次发出相同通知？

当前企微 SDK 的回执等待会超时并拒绝 Promise；主动 `sendMessage` 每次生成新的 req_id。因而“超时”不能等同于“对方一定没有收到”，本地去重也不能证明远端恰好一次。[SDK 回执处理](https://github.com/WecomTeam/aibot-node-sdk/blob/80615b987ef69c6028ad764924609247c0725955/src/ws.ts#L518)、[主动发送](https://github.com/WecomTeam/aibot-node-sdk/blob/80615b987ef69c6028ad764924609247c0725955/src/client.ts#L346)

最小修正：在一个数据库事务内写入接收记录、answer ID 和生成任务；定义 `queued/running/completed/failed/cancelled` 等终态与工作者租约，过期工作者不能覆盖新尝试。网页 `POST /answers` 使用有范围的幂等键和请求摘要，同键同内容返回同一 answer，同键不同内容报冲突。已经外发的答案要有持久化片段或明确的不可恢复失败策略。把业务层的唯一逻辑答案与模型调用次数分开：崩溃重试可能再次计算，不能在缺少供应方支持时承诺调用绝对不重复。

为每个渠道保存独立的投递状态，区分确认成功、明确失败和结果未知。先实测平台是否支持指定业务 ID 的幂等投递；不支持时明确通知可能重复的语义，用稳定通知编号处理用户体验，避免无条件宣称“绝不重复”。

关闭证据：在接收、排队、生成、持久化、发送、收到回执之间逐点杀进程和重放请求；同一请求能在限定时间进入终态；旧工作者不能覆盖新结果；发送结果未知不会被当作确定失败或成功。

**F4 · [P2] 经过评估的发布单元没有完整覆盖实际生成配置**

依据：[发布单元 L130](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L130)、[请求装配 L146–151](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L146)、[容量绑定 L259](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L259)。

文档已绑定内容、索引、检索配置、角色提示词与评估，也要求容量绑定模型版本，这是正确方向。但是激活契约没有规定公司模型部署版本、公共系统提示词、生成参数和输出协议版本如何进入同一基线。问答步骤又把角色配置读取与知识版本固定并行描述，若读取的是各自“最新配置”，会拼出未经评估的组合。

反例：候选使用模型部署 M1、提示词 P1 通过评估；上线后公司网关别名指向 M2，或独立发布 P2。知识 release ID 保持不变，现有引用和版本校验继续通过，但质量及容量依据已变。

最小修正：先读取不可变的发布描述对象，再按其中明确的配置版本并行加载。增加运行配置摘要，至少覆盖模型部署标识/可获得的版本、生成参数、系统与角色提示词、检索和分段协议、评估题集版本。逐请求保存实际使用值。供应方无法固定底层模型时，要记录这一可重复性限制，并建立变更检测与回归方式。

关闭证据：在回答装配期间切换 active 或配置，单个回答仍全部使用同一发布描述；修改模型配置或公共提示词后，旧评估不会被当作新组合的通过证明。

**F5 · [P2] 企微连接归属和流式发送协议需要补齐**

依据：[工程部署 L56](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L56)、[分段输出 L173–175](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L173)、[计时口径 L238、257](https://github.com/OptionsRight/wikiBot/blob/3f847e074b533c863af7970a03624434e8cef640/docs/handoff/domain-knowledge-bot-design-v0.2.md#L238)。

已从官方 SDK 源码核实：同一 Bot 新连接建立会触发旧连接断开处理；流式回复沿用相同 stream ID 刷新内容；内容限制按 UTF-8 字节计算；回复按 req_id 等待回执。同一 Bot 的两个入口副本不能简单各自独立连接，内部答案块也不能直接当作独立的追加消息假定发送。[连接断开处理](https://github.com/WecomTeam/aibot-node-sdk/blob/80615b987ef69c6028ad764924609247c0725955/src/ws.ts#L245)、[流式类型](https://github.com/WecomTeam/aibot-node-sdk/blob/80615b987ef69c6028ad764924609247c0725955/src/types/api.ts#L89)

最小修正：首版明确每个 Bot 只有一个拥有连接的入口实例，计算 worker 可以并发；如果需要入口高可用，再实现有防旧实例写入能力的接管机制。适配器维护稳定的 answer/stream/req_id 映射，累计已经通过校验的内容，合并待发更新，发送结束帧后按回执记录结果。必须规定字节超限、断线、连接切换、群身份校验失败时的行为。

撤回检查应放在实际发送调度点，避免内容在应用检查后长期滞留 SDK 队列。已进入网络的消息仍遵循文档承认的在途限制，不承诺原子撤销。

关闭证据：同时启动两个入口、滚动替换入口、延迟/丢失回执、断线、连续分段、超过字节上限及撤回时有排队内容；验证连接可控、文字不被后续块覆盖、不会无界积压，最终发送状态与 SLO 统计一致。

**对已有 R1–R6 复查结论的处理**

已有报告明确限定为设计层面的聚焦复查，没有声称接口或性能已经验证。这一点应保留。不能仅因尚未跑测试，就把它所有“已解决”改成错误。

- R1 的领域受众与私有历史边界成立；群成员范围能否真实核验，仍是启用群聊的阻断条件。
- R2 的父版本 CAS 方向成立，但 F2 要求把共同并发边界和失效范围写成可执行契约。
- R3/R4 的维护窗口、快照和专家更正记录可保留；需要真实工作区往返验证，没有证据要求重做成常驻同步平台。
- R5 的联合 SLO 与引用门禁方向成立；F1 补的是结构校验之外的完整性判定，F5 补的是企微适配。
- R6 已正确承认历史消息无法保证消失；F3/F5 补的是通知结果未知、重试和排队发送的处理。

**仍需实测的三项外部条件**

| 条件 | 需要的证据 | 不满足时如何处理 |
|---|---|---|
| 公司模型服务 | 固定连接及部署版本，流式分段遵循、长答案、取消、超时、配额、真实生成耗时 | 调整模型/输出方案；如工具调用不适配，先验证一次生成路径并调整复杂问答范围 |
| 企业微信与公司身份 | 明确 Bot 类型；userid 与 SSO 映射；目标群访问范围；主动通知及连接切换行为 | 无法验证群范围时只启用已认证网页或获准单聊，不能假定 SDK 自动提供群成员授权 |
| llm_wiki 工作区 | 固定版本，冻结写入、导出、改名、引用和附件解析、专家更正后重新导入及再次发布 | 无法可靠暂停时使用不可变人工导出包；往返失败前不宣称反馈闭环完成 |

官方 llm_wiki 是桌面工作区，文档确认了 Markdown、来源追溯和本地 API。独立快照发布符合这些边界；上线服务不能把桌面运行状态当成自己的可用性保证。[llm_wiki 说明](https://github.com/nashsu/llm_wiki/blob/e8082119649e6a8e1cf85eaf289adcabfdf39d4e/README.md)

SDK 的事件类型和消息字段并不构成群成员名册。原生引用消息在已检查的类型中主要包含引用内容，没有可直接依赖的原答案 ID；阶段 0 应检查实际回调。无法可靠关联时，引用文本只作为不可信输入，使用平台保存并授权核验的 answer ID 读取历史，不从一段引用文字推断有权读取完整答案。[企微消息类型](https://github.com/WecomTeam/aibot-node-sdk/blob/80615b987ef69c6028ad764924609247c0725955/src/types/message.ts#L80)

**落到开发任务前需要固定的材料**

无需再扩充一套平台。补齐五份短规格即可：

1. 流程页与答案协议：实际 schema、必填项、分支选择、澄清、引用、完整性、结束和失败事件。
2. 发布迁移表：每个操作的合法起点、权限、前置基线、共同事务边界、失败结果和修复入口。
3. 消息与作业迁移表：请求幂等范围、Answer/Attempt 终态、失联清理、允许重试的条件、投递未知状态。
4. 企业微信适配说明：连接归属、流 ID、累计输出、回执、字节限制、身份与群范围。
5. 验收矩阵：每个关键行为的样本、预期、责任人、通过条件和失败后的产品范围。

版本化 JSON Schema、少量正常/异常样本以及状态表足以作为第一版规格；完整数据库 DDL 和所有代码细节可以随实现细化。快照幂等还应明确同一 submission ID 重试相同包返回原结果，重试不同包返回冲突，避免把“ID + hash”误实现成允许同 ID 多次提交不同内容。

质量验收应固定分支、前置条件、禁止结论、缺知识及旧版本样本，区分协议通过、证据支持、完整清单和真正解决问题。30–50 条题可作为首批人工基线，不能仅靠重复同一批题 1,000 次证明知识泛化。

性能继续使用原文的联合指标：在声明负载档位下，至少 95% 的普通请求同时满足首段有用内容 ≤3 秒、完整回答 ≤10 秒和成功条件。必须先固定该档位、输出长度、样本组成和成功定义，再测量。首个闭合结构块的时间要实际测，不能用收到第一个原始 token 的时间替代。已有 256/512/1,500 token 数值是待调预算，并非不可行性的证据，也并非性能通过证明。

上线前另需最小运维说明：入口/worker 部署与健康检查、数据库及不可变内容恢复、迁移失败处理、卡死作业和通知失败告警、可执行的撤回/回滚步骤。恢复后的 active 指针、内容包与索引仍须一致。保存 30 天目前是待确认假设，应说明会话删除如何影响反馈证据与审计记录。

**Pi 的位置**
